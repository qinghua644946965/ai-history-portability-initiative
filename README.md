# AI 会话与任务数据可携带访问能力

**中文** | [English](README.en.md)

**Initiative Draft v0.1 · 用户倡议 / 开放讨论稿**

**Ownership · Portability · Interoperability**

**我们倡议 AI 服务商开放用户自身会话与任务数据的持续提取能力：经用户授权，以只读方式分页获取记录，并支持稳定增量定位。**

## 一、从真实经历出发：智能的 AI，手工搬运的历史

这份倡议来自一名日常使用 AI 处理工作、技术问题和构想的用户。最直接的困惑，是一种体验上的反差：

> 我已经能让 AI 帮我写软件、分析资料、讨论复杂问题；但如果持续取回自己的交互历史，仍要经过“设置 → 申请导出 → 等待 → 下载压缩包 → 解压 → 自己处理”，数据管理就仍然停留在手工搬运档案的方式里。

当 AI 能参与复杂工作，而用户保存历史仍依赖反复导出时，智能能力与数据访问便利性之间就出现了落差。这段流程概括的是本倡议关注的使用痛点，并非对所有平台导出步骤或接口现状的统一描述。

用户希望能够持续保存、查阅和整理自己的历史。无论以后怎样使用这些数据，都应先回答这个朴素的问题：**为什么不能通过稳定的只读接口，持续取回自己有权访问的交互记录？**

在发起者提供的经历线索中，有两个具体入口。一个是在 Codex 中搜索“表格”的案例，涉及不同操作或历史加载状态下的搜索结果差异。**此案例目前待补证据、待核验**：本文不确认结果数量，也不把差异归因于仅搜索已加载内容、索引范围或其他内部机制。另一个是试图找回关于“FLV 无声音”的既往讨论。**此案例同样待补原始证据**：本文不确认具体发生日期、客户端版本、检索步骤及最终结果。

这些是用户报告的观察线索，不是已经完成复现的产品缺陷报告，更不能据此断言数据丢失或厂商有意阻碍访问。它们提出的问题仍然值得讨论：如果记录存在且用户有权访问，能否让用户自行保存、建立索引，并在以后可靠地回到原始上下文？证据状态和补证要求见 [evidence/](evidence/README.md)。

## 二、问题：记录留在平台，不等于用户能够长期使用

AI 会话承载的往往不只是最终答案，还包括问题怎样被澄清、某个方案为什么被否定、约束如何变化，以及一项任务最终如何完成。只复制结论，可能失去判断成立的条件；只保留摘要，也难以重新检查其中的遗漏与误解。

随着会话和任务不断积累，用户需要记住讨论位置、会话标题和关键词。平台内搜索可以改善找回体验，但用户仍可能希望自行备份、建立索引、按项目归档，或回看一项判断的形成过程。即使只使用一个平台，而且它的搜索足够优秀，这种自主保存和组织数据的需求也依然存在。

本倡议关注的是用户能否持续取得自己有权访问的会话与任务数据，并决定其后续用途。取回数据的能力应当独立成立，无需以建设知识库或采用某种 AI 工作方式为前提。用户即使只想保留一份可阅读、可检索的记录，也应当有实用的选择。

## 三、为什么一次性 Export 不够

一次性 Export 对备份、迁移和留档有价值。问题在于，持续使用 AI 会不断产生新记录，也可能修改已有内容。如果每次更新都要重新申请、下载、解压全量文件，再自行比较差异，那么持续维护档案就会变成重复劳动。

全量快照回答的是“这次拿到了什么”，持续同步还需要回答“上次之后新增或改变了什么”“中断后从哪里继续”“哪些内容未包含在返回范围内”。没有稳定的定位和范围说明，用户侧工具就难以判断重复、遗漏与同步完成状态。

因此，我们希望在保留导出的同时，提供适合持续使用的数据访问能力。它不必实时，也不必承诺无限吞吐；合理的延迟和限流可以接受。但限制应公开、可理解，使用户能够安排下一次同步，而不是长期依赖手工搬运。这里讨论的是能力需求，不是对所有现有产品功能的统一断言。

## 四、最低诉求：一条稳定、可持续的数据出口

**AI 可以极其先进，数据接口甚至可以极其朴素。** 我们只希望有一条稳定的管道，可以持续取回自己的数据。它的基本过程可以很简单：用户授权 → 只读、分页获取记录 → 保存游标或检查点 → 下次增量同步。

我们倡议 AI 服务商逐步提供以下最低能力：

1. **用户授权。** 用户能够明确选择授权范围和接收工具，并撤销未来访问。授权范围应当可理解，不能把取回记录等同于同意无限制二次使用。
2. **只读访问。** 允许用户或其授权工具程序化读取用户有权访问的会话与任务记录。范围应覆盖理解交互所需的可见内容、必要元数据及记录关系；附件、产物和可见工具结果的支持范围与缺失情况应明确说明。
3. **分页查询。** 历史较长时，可以分批读取，并有明确的结束或继续标记，避免把单次返回误认为全部历史。
4. **稳定增量定位。** 提供游标、检查点或等效能力，使同步可以继续、重试并识别变化。说明是否包含更新与删除标记，以及定位失效后的恢复方式。
5. **可理解的运行约定。** 公开数据范围、格式说明、身份标识规则、保留期限、限流与错误处理方式，并说明不兼容变更如何通知。

上述诉求描述用户需要达成的结果，不规定端点名称或统一字段。可以从有限范围的只读访问起步，但应如实说明缺口。提供商决定内部实现，用户侧工具负责适配、索引与整理。

## 五、明确边界：保持最低诉求可落地

这是一份 **Initiative Draft v0.1**，不是白皮书、协议标准、认证规范或已形成的行业共识。它不要求统一厂商内部 Schema、数据库、Memory、知识图谱或 Agent 架构，也不要求实时推送、Webhook、统一轮询频率或固定性能指标。

访问范围限于用户本来有权访问的数据，不包括模型权重、隐藏推理、内部系统提示、商业机密及其他用户的私有内容。多方参与的记录与第三方材料仍须遵守相应权限边界。提供数据出口也不意味着厂商必须替用户建设知识库，或永久保存已经删除的内容。

用户控制数据的同时，需要管理接收工具的授权、存储和再次分享。撤销平台授权可以阻止后续读取，却不应被描述为自动删除所有已下载副本；接收工具应清楚说明其副本管理方式。

本文提出的是产品原则与用户诉求，不作特定法域的法律结论。数据可携带可能降低切换成本，也可能与平台留存激励产生张力；这是需要讨论的推断，不能据此认定某家厂商故意锁定用户或违反法律。

## 六、原则与结语

**Ownership** 意味着用户对自己有权访问的交互历史拥有实质控制能力；这里不把所有记录的知识产权归属一概而论。**Portability** 意味着用户能够持续把记录带到自己选择的系统。**Interoperability** 意味着用户可以授权不同工具和模型使用这些历史，而不必等待所有平台采用同一种内部结构。

我们希望用户选择平台，来自产品的价值。无论用户长期留在一家服务，还是以后更换平台，都应能够持续保存和使用自己的记录。取回数据之后如何利用，由用户自行决定；思考与工作的连续性应当由用户自己掌握。

**AI 可以更换，用户的认知历史不应该随平台更换而丢失。**

**Data stays with the user. Intelligence competes above it.**

欢迎用户补充可核验、已脱敏的案例，也欢迎服务商和开发者指出成本、限制与可行路径。我们从一个有限请求开始：让用户能够经授权、只读、分页并支持稳定增量定位地，持续取回自己的 AI 会话与任务数据。
